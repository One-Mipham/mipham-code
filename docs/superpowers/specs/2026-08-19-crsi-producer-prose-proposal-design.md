# CRSI Producer 散文提议 — A1 边界决策

> **日期**: 2026-08-19
> **作者**: Guohua Zhang · One Mipham Corporation
> **术语**: CRSI（Continuous Recursive Self-Improvement）；A1 铁律 = 绝不拿 LLM 当裁判（自改进的判定环节不得依赖被改进对象自身打分）
> **前情**: 承接 [[2026-08-19-crsi-behavior-task-suite-design]]（行为任务集 M1）与 [[2026-08-08-phase-10-crsi-experience-driven-evolution-design]]（CRSI 三层学习）

---

## 一、背景与问题

**producer 现状**（`core/crsi-producer.ts`）：只产**确定性规则**（`timeout` / `tool-params` 两类，`renderManagedRuleSource` 模板化、无 LLM）。不能产**散文修改**（改 skill 正文 / prompt / 代码）。

**死结**：

```
producer 改散文
  → 需「证明改好了」
    → 误以为 = 「LLM 评文字质量」（A1 禁止）
      → 卡死，不敢改散文
```

**解法结论**（已在行为任务集 spec 确立）：散文的「证明更好」**不等于**「LLM 评文字质量」，而**等于**「行为效果度量」（确定性 ground-truth，A1 允许）。本 spec 把这一结论钉进 A1 的**精确定义**，并回答块 1（producer 引入 LLM 生成）是否破 A1。

---

## 二、A1 铁律的精确定义

A1 禁止的不是「LLM」，而是「**LLM 当判定**」。这两个常被混为一谈，必须钉死：

| 判断类型       | LLM 在干什么                               | 结果是什么             | A1      |
| -------------- | ------------------------------------------ | ---------------------- | ------- |
| **生成性判断** | 生成候选时，token 层面隐含地选「哪个更好」 | 一个**候选**           | ✅ 允许 |
| **判定性判断** | 显式、权威地裁决「接受 / 拒绝 / 打分」     | 一个**裁决**，直接固化 | ❌ 禁止 |

**关键论证**：LLM 生成任何东西都隐含判断——生成代码时在「判断」代码写得好不好，生成散文时在「判断」句子通不通。若把这种隐含判断也算「裁判」，A1 就变成「LLM 什么都不能做」（连行为任务集里「LLM 生成行为」也违规），这显然不是 A1 的本意。

A1 的本意是：**禁止 LLM 的判断拥有最终权威（裁决权）**。

- 生成性判断的结果是「候选」，候选还要过独立的判定链（确定性 + 人）才固化 → LLM 的判断没有权威 → 不破 A1。
- 判定性判断的结果直接固化 → LLM 篡夺权威 → 破 A1。

**分界线：LLM 的判断结果是「一个候选」还是「一个裁决」？** 候选不破 A1，裁决破 A1。

---

## 三、块 1 的 LLM 定位：生成侧

块 1 不是「把 LLM 引入 CRSI 闭环」，而是「**把生成器从模板升级成 LLM**」，判定链原地不动：

|               | 生成器                            | 判定链                     |
| ------------- | --------------------------------- | -------------------------- |
| producer 现在 | 模板（`renderManagedRuleSource`） | 结构预筛 → 测试 → 人审     |
| 块 1 之后     | LLM（从失败信号生成散文提议）     | 结构预筛 → 行为效果 → 人审 |

唯一的增量是「生成器」一栏从模板换成 LLM。**判定链一栏完全没变**——它一直是「确定性的 + 人的」，LLM 从来不在判定侧。

**结论**：块 1 在字面上、结构上都不破 A1。

---

## 四、真正的风险：判定权渐进架空（精神层）

只聊到 §三，是「字面不破」。A1 的精神（防止自我讨好漂移）还有一个隐蔽威胁：

**若 LLM 生成的候选质量太高，人审会退化成橡皮图章**——人类每次看到「改得挺对的」就点批准。此时 LLM 的**生成性判断**就**事实上**取得了判定权：形式上人审还在，实质上 LLM 在判。

这是渐进失效（drift），不是一次性破 A1，但它是 A1 精神的更深层威胁。**块 1 的决策实质，不是「要不要 LLM 生成」，而是「如何在引入 LLM 生成的同时，保证判定仍然真实地落在确定性闸 + 人手里，而不是被 LLM 的生成质量架空」。**

---

## 五、根解：把「证明更好」劈成两个 LLM 碰不得的判定

传统的死结之所以是死结，是因为把「证明散文改好了」等同于「LLM 评文字质量」。而**「文字质量」压根不该是判定对象**。

「证明更好」应劈成两个不同质的问题：

| 判定         | 谁来判                                 | 为什么 LLM 不能碰        |
| ------------ | -------------------------------------- | ------------------------ |
| **行为更好** | 确定性 ground-truth（行为任务集第②层） | LLM 判 = 自我讨好        |
| **方向正确** | 人                                     | 人的价值特权，LLM 无资格 |

而「文字质量」是**生成侧的隐含产物**——LLM 生成候选时的副产品，由「行为效果」间接验证：行为效果过了，文字质量自然达标；行为效果没过，文字写得再漂亮也没用。**它不需要独立判定，因为它不是目的，只是手段。**

死结的彻底解：**用「行为效果（确定性）+ 方向（人）」两个判定，替代「文字质量（LLM）」这一个判定。**「文字质量」退出判定舞台，降级为生成侧的内部指标。

> **术语澄清**：本文「行为任务集的第二层（任务表现）」（§五）与「三层验证的第②层（行为效果）」（§六）是**同一机制（M3/A 任务表现度量）**——前者从「任务类型」命名，后者从「验证阶段」命名。全文「第②层」均指 M3/A 任务表现度量，不另设概念。

---

## 六、三个结构性约束（锁死判定权）

A1 不破的**充分条件**，是下面三个约束落地——否则就是「字面不破、精神破了」：

1. **证据链强制** — 每条散文提议必须附「失败信号证据」（`CrsiSignal.evidence`），人审有据可依，不是空洞地评「改得好不好」。这让「方向正确」的判定有锚点，人审难以被架空。

2. **每次一条 + 范围预筛在前** — producer 每次只产 1 条提议；结构预筛（`proposal-guard.ts`，已落地）在 LLM 生成**之前**就卡死「能改什么范围」（只 skill / managed-rule，且不可碰裁判机制）。LLM 的生成自由被结构性收窄，其隐含判断跑不出安全域。

3. **行为效果是硬闸，人是软闸** — 固化前必须过第②层（行为效果不退化）；人审只做「方向正确」（符合愿景/宪法），不做「质量判断」（那是 LLM 的活，A1 禁）。人审从「质检员」降为「守门员」——只否决明显跑偏的，不逐字审质量。

---

## 七、结论

块 1 的 A1 边界决策：**允许 LLM 生成候选，不破 A1**——因为判定链（确定性 + 人）从未被 LLM 接管；真正的工程任务是**用「证据链 + 范围预筛 + 行为效果硬闸」三件事，防止人审被 LLM 的生成质量架空**。这不改变 A1，反而是 A1 精神（防漂移）的落地。

## 八、实现状态（块 1 核心已落地）

块 1 的核心（producer 散文提议）已于 2026-08-19 落地（可控 MVP，两阶段 LLM）：

1. **producer 怎么接 LLM 生成** — ✅ 已落地：`selectTargetSkill`（阶段 1 选目标 skill）+ `generateProseContent`（阶段 2 读原文增量生成）+ `produceProseProposal`（编排）。LLM 作参数注入，prompt 模板版本化常量。skill 列表 + 原文读取依赖注入。
2. **失败信号的选择与去重** — ⏳ 仍开放：复用 `selectCrsiSignal` 选信号，但「同一信号反复产出相同提议」的幂等（稳定 hash）未做，留待人审 + 后续。
3. **第②层行为效果（M3/A）的「代码来源」** — ✅ 已解决：见 [[2026-08-19-crsi-end-to-end-task-runner-design]]（C 基建，端到端任务运行器 + 改前/改后对比）。

**尚未接线**：`/crsi propose` 命令尚未把 `produceProseProposal` 接进 CLI 流程（需在 commands.ts 收集 skill 列表 + 读原文 + 走 prefilterProposal → 沙箱 → 人审）。这是块 1 的最后一步「接线」。
