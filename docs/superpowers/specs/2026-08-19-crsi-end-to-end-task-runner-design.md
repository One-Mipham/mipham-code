# CRSI 端到端任务运行器（行为效果度量基建）设计

> **日期**: 2026-08-19
> **作者**: Guohua Zhang · One Mipham Corporation
> **术语**: CRSI（Continuous Recursive Self-Improvement）；A1 铁律 = 绝不拿 LLM 当裁判
> **前情**: 承接 [[2026-08-19-crsi-producer-prose-proposal-design]]（A1 边界决策，§八.3 的 M3/A 代码来源抉择）与 [[2026-08-19-crsi-behavior-task-suite-design]]（行为任务集 §三 的 A/B 抉择）

---

## 一、背景与动机

**A/B 抉择是范畴错误**（已在前情 spec 聊透）：行为任务集 §三 的「代码来源」A（LLM 生成代码）/ B（冻结代码）都度量不到「改散文的效果」——因为块 1 改的是 skill 散文，影响的是 agentic 行为（skill 引导下的规划/工具调用），不是原始代码能力。

**真选项 C（端到端）**：冻结一批有 ground-truth 的任务 → 让 Mipham Code（注入改后的散文）完整跑 → 判定 ground-truth 对错。这才是「行为效果」的真义。

本 spec 落地 C 的基建决策：**端到端任务运行器**，它是块 1「行为效果硬闸」的地基。

---

## 二、核心决策：真实 LLM + 确定性判定 + 统计控制

### 2.1 llm-replay 反证「C 不能走假捷径」

现有 `providers/llm-replay.ts` 的 `replayLlm(turns)` 的 `chat()` **忽略传入的 `ChatRequest`**（直接回放预录 chunks，不读 system prompt）。而散文通过 `ChatRequest` 的 system prompt 进入 LLM。所以回放/scripted LLM **不消费散文**——度量不到散文效果。

**结论**：C 的 LLM 源**本质必须是真实 LLM**（消费改后散文，产生真实响应）。

### 2.2 三个环节的归属

| 环节       | 谁                      | 说明                                        |
| ---------- | ----------------------- | ------------------------------------------- |
| 生成行为   | **真实 LLM**            | 消费改后散文，产生真实 agentic 行为         |
| 判定       | **确定性 ground-truth** | 测试过没过 / 答案对不对 / 工具序列——不破 A1 |
| 非确定控制 | **统计**（不是回放）    | temperature=0 + N 次采样 + 通过率分布对比   |

> **llm-replay 的正确用途**：不是「度量散文效果」，而是「测试可复现」——隔离非 LLM 部分的 bug。度量散文效果必须真实 LLM + 统计。

### 2.3 代价可接受性

真实 LLM 的「慢 / 贵 / 非确定」是 C 的本质代价，无法绕过。但 C 是**低频验证**（producer 改散文时才跑），非高频 eval——故可接受。

## 三、四组件架构

| 组件            | 内容                               | 复用点                                    |
| --------------- | ---------------------------------- | ----------------------------------------- |
| 冻结任务集      | 有 ground-truth 的任务（人类冻结） | 新建                                      |
| headless runner | 驱动 engine 跑完一个任务           | 复用 `QueryEngine.process()` + `setLlm()` |
| 隔离            | 跑任务不改真实工作区               | MVP 用 tmpdir；改真实文件时用 worktree    |
| 判定器+统计层   | 确定性判对错 + N 次采样统计        | 新建                                      |

### 3.1 冻结任务集（新建）

任务类型（MVP 从最简单开始，逐类扩展）：

| 类型     | 任务指令示例                      | ground-truth       | 判定语义   |
| -------- | --------------------------------- | ------------------ | ---------- |
| 代码生成 | 「实现函数 X，写到 `tmp/foo.ts`」 | 冻结 vitest 测试   | 测试过不过 |
| 工具调用 | 「用 bash 查 Y 文件的行数」       | 期望的工具调用序列 | 序列匹配   |
| 问答     | 「回答 Z」                        | 标准答案           | 答案比对   |

- 人类冻结，延续 behavior-tasks 的「人类冻结、无 LLM」精神，存为源码内 JSON（版本控制）。
- **独立性要求**（承接行为任务集 spec §九.1）：任务不得依赖被改的散文本身，否则「改了散文 → 任务也变 → 无法前后对比」。冻结的任务 prompt 是硬编码的，天然独立。

### 3.2 headless runner（复用 engine）

- `QueryEngine.process(userInput)` 是**完整 agentic loop**（hooks / DLP / 工具执行 / compaction 均在内）。
- `getSystemPrompt()` 是散文进入 LLM 的地方（skill 注入在此反映）。
- `setLlm(llm)` 缝让 runner 注入**真实 provider 的 Llm**（`ProviderRegistry implements Llm`）。
- runner 的职责：构造 engine → `setLlm` → 喂任务指令 → 消费 `process()` 到任务完成 → 交由判定器。

### 3.3 隔离（复用）

- **MVP**：代码生成任务写 cwd 内的 git-ignored 目录（`process.cwd()/.mipham/task-runner`），不碰真实仓库源文件。**架构约束**：Write 工具的 `resolveSafe` 强制「写文件必须在 cwd 内」（`engine.executeTool` 硬编码 `cwd: process.cwd()`），故产物不能写系统 tmpdir（会被拒）。
- **成熟**：若任务要改真实文件，复用 `CrsiSandbox` 的 worktree 机制。

### 3.4 判定器 + 统计层（新建）

- **判定器**：确定性——跑冻结测试 / 比对工具序列 / 比对答案。纯 `passed: <boolean>`，零 LLM。
- **统计层**：同一任务跑 N 次（temperature=0），得通过率。对比「改前 vs 改后」的通过率分布，判「行为更好」。

## 四、数据流

```
度量「改散文效果」= 对比改前 / 改后两轮：

baseline 轮（改前散文）:
  engine.setLlm(真实 Llm) → 喂任务指令 → process() 完整跑 → 判定 → 通过率 P0（N 次采样）

candidate 轮（改后散文）:
  同上，但 getSystemPrompt() 反映改后散文 → 通过率 P1（N 次采样）

判定「行为更好」: P1 显著高于 P0（显著性阈值见 §七.3）
```

---

## 五、MVP 路径

别一上来建完整任务集。MVP 只验证一件事：**「端到端度量」这条链跑得通**。

- **1 个冻结任务**（代码生成，ground-truth = 冻结 vitest 测试）
- 复用 `engine.process()` + `setLlm(真实 provider)` + tmpdir 隔离
- 跑 N 次（temperature=0），统计「测试通过率」
- 跑通后，再扩任务集（工具调用 / 问答）+ 加改前改后对比

---

## 六、非目标

- ❌ 实现块 1 的 LLM 生成（那是 producer 散文提议，独立 spec）。
- ❌ 度量「文字质量」——那是 LLM 裁判的盲区，本 spec 范围外。
- ❌ 用 LLM 判「行为好不好」——判定一律是确定性 ground-truth（A1 铁律）。
- ❌ 高频 eval——C 是低频验证，只在改散文时跑。

---

## 七、风险与开放问题

1. **真实 LLM 的成本 / 非确定**：低频验证缓解成本；非确定靠统计。但需设定采样次数 N 的默认值（如 5 次起步）。
2. **统计显著性**：P1 比 P0 高多少算「显著更好」？小样本下显著性不可靠，需设一个诚实的阈值（如「P1 不低于 P0，且至少 1 次成功」作为第一版弱判，强判留待更多采样）。
3. **任务集的可持续冻结**：谁、何时、按什么节奏冻结新任务？建议「每次 CRSI 发现新失败模式，冻结对应任务」，与 producer 的失败信号节奏对齐。
4. **任务运行器的 provider 选择**：C 用哪个 provider 的 Llm？应与 Mipham Code 生产环境的默认 provider 一致，否则度量的是「别的模型的行为」。

---

## 八、与 A1 边界 spec 的关系

C 是块 1「行为效果硬闸」（[[2026-08-19-crsi-producer-prose-proposal-design]] §六约束 3）的**地基**。没有 C，「证明更好」就退化成「结构合法 + 方向正确」，缺「行为更好」这一环。

**当前状态**：块 1 的「行为效果硬闸」是 **stubbed**（依赖 C，C 未建）。在 C 落地前，块 1 的「证明更好」只能靠「结构预筛 + 人审」两闸，行为效果由人审兜底。

## 九、里程碑

| 里程碑 | 内容                                    | 交付物                                   |
| ------ | --------------------------------------- | ---------------------------------------- |
| C-MVP  | 最小任务运行器（1 任务 + 统计）         | 冻结任务 JSON + runner + 判定器 + 统计层 |
| C-2    | 改前/改后对比 + 显著性弱判              | 通过率对比 + 「不退化」闸                |
| C-3    | 任务集扩展（工具调用 / 问答）+ 隔离升级 | 多类任务 + worktree 隔离                 |

**C-MVP 是本 spec 的完整实现范围**。C-2/C-3 是扩展点。
